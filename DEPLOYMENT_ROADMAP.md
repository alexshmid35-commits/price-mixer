# Price Mixer — План Доработок И Публикации На Сервер

## 1. Цель

Подготовить проект к стабильной работе в продакшене (сервер), сохранив текущую логику сводного прайса и улучшенный поиск `OnlinerID` для позиций без ID.


## 2. Что Уже Сделано

- Улучшен поиск `OnlinerID` для товаров без ID:
  - убрана подстановка "первого результата" без проверки;
  - добавлен более строгий матчинг по артикулу/названию;
  - улучшено извлечение артикулов (в т.ч. сложные варианты).
- Логика для товаров с уже указанным `OnlinerID` в прайсе сохранена.
- Сводный прайс формируется по прежнему принципу (лучшая цена, поставщик и т.д.).


## 3. Бэклог Доработок (Перед Продом)

### 3.1. Качество Сопоставления

- [ ] Добавить `confidence_score` (оценка уверенности сопоставления).
- [ ] Добавить статус результата: `AUTO`, `REVIEW`, `REJECT`.
- [ ] Добавить лист/выгрузку "Требует проверки" для спорных позиций.
- [ ] Подключить "эталонную" базу `mapping_verified` (проверенные вручную пары `артикул -> onliner_id`).

### 3.2. Хранение Данных

- [ ] Перенести кэши (`onliner_id_cache`, URL cache) из JSON в БД.
- [ ] Добавить таблицу истории сопоставлений (когда/кем подтверждено).
- [ ] Добавить очистку старых папок `uploads` по TTL (например, > 14 дней).

### 3.3. Надежность

- [ ] Вынести фоновые задачи поиска ID в worker (Celery/RQ + Redis).
- [ ] Добавить таймауты/повторы API-запросов с ограничениями.
- [ ] Добавить журнал ошибок и событий.

### 3.4. Безопасность

- [ ] Перенести секреты/API-ключи в переменные окружения.
- [ ] Ограничить размер загружаемых файлов.
- [ ] Проверять расширение и MIME загружаемых файлов.
- [ ] Добавить авторизацию в интерфейс загрузки (если доступ в интернет открыт).


## 4. Чек-Лист Публикации На Сервер

## Этап A — Подготовка Локально

- [ ] Прогнать сценарии на 3-5 реальных наборах прайсов.
- [ ] Проверить, что:
  - товары с `OnlinerID` из прайса сопоставляются корректно;
  - товары без ID получают ID только при уверенном совпадении;
  - спорные позиции остаются пустыми/попадают в review.
- [ ] Зафиксировать версию (тег/архив), которую отправляем на сервер.

## Этап B — Подготовка Сервера

- [ ] Подготовить окружение:
  - Python (совместимая версия),
  - виртуальное окружение,
  - зависимости проекта.
- [ ] Установить и настроить:
  - `gunicorn` (приложение),
  - `nginx` (reverse proxy + SSL),
  - `redis` (если используется worker-очередь).
- [ ] Подготовить папки:
  - рабочий каталог приложения,
  - каталог логов,
  - каталог временных загрузок.

## Этап C — Конфигурация

- [ ] Создать `.env` (или системные env):
  - `FLASK_SECRET_KEY`,
  - ключи внешних API,
  - пути к БД/кэшам,
  - лимиты загрузок.
- [ ] Настроить `nginx`:
  - домен,
  - HTTPS (Let's Encrypt),
  - проксирование в `gunicorn`.
- [ ] Настроить запуск как сервис (`systemd`/docker compose).

## Этап D — Первый Деплой

- [ ] Развернуть код на сервере.
- [ ] Запустить сервисы.
- [ ] Проверить:
  - главная страница открывается;
  - загрузка прайса работает;
  - формируется `consolidated_price.xlsx`;
  - кнопка "Найти ID" работает;
  - загрузка результата работает.
- [ ] Проверить права на запись в `uploads` и в хранилище кэша/БД.

## Этап E — Приемка После Публикации

- [ ] Прогнать контрольный тест на реальных данных.
- [ ] Сравнить результаты с локальной версией.
- [ ] Проверить логи ошибок за первые 24 часа.
- [ ] Включить ежедневный backup (БД/кэши/важные конфиги).


## 5. Операционный Режим (После Запуска)

- [ ] Регламент ручной проверки спорных ID (например, 1 раз в день).
- [ ] Пополнение `mapping_verified` по результатам проверки.
- [ ] Еженедельная проверка метрик:
  - `% AUTO`,
  - `% REVIEW`,
  - доля ложных совпадений по выборке.
- [ ] План обновлений: сначала staging, потом production.


## 6. Критерии Готовности К Продакшену

Считаем систему готовой к устойчивой работе, когда:

- [ ] Ошибки ложного сопоставления сведены к минимуму на контрольной выборке.
- [ ] Есть процесс review спорных позиций.
- [ ] Есть резервное копирование.
- [ ] Сервисы автоматически перезапускаются при падении.
- [ ] HTTPS и базовая защита загрузок включены.
