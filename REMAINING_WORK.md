## Достигнут ли максимум после перехода на SQLite

Нет. Переход каталога Onliner и постоянных состояний на SQLite убрал важный
файловый bottleneck, но не исчерпал резерв производительности.

Уже сделано хорошо:

- каталог примерно на 800 тысяч вариантов хранится в SQLite;
- для поиска используется FTS5, для параллельного чтения включён WAL;
- основные очереди, ручные привязки и результаты зелёного подбора сохраняются
  надёжно;
- главная таблица использует серверную пагинацию и не рисует весь прайс в DOM;
- в зелёном подборе есть дедупликация одинаковых товаров, пул до 8 workers и
  пакетная запись результатов.

Оставшиеся узкие места по текущему коду:

1. рабочий прайс сессии всё ещё хранится одновременно в pandas, JSON и XLSX;
2. первый запрос новой ревизии прайса всё ещё проходит все строки, но
   повторные страницы и одинаковые поиски используют ограниченный кэш;
3. изменение ID может приводить к повторной сериализации JSON и XLSX;
4. подбор кандидатов выполняет отдельную цепочку SQL-запросов и Python-scoring
   для каждого уникального товара;
5. статические CSS/JS кэшируются на пять минут; для долгого immutable-кэша
   ещё нужна версия URL ассетов;
6. `app.py` содержит около 5 400 строк, а крупные модули matching/review
   затрудняют безопасную оптимизацию и повторное использование кода.

SQLite пока подходит лучше всего: приложение работает на одном компьютере,
каталог в основном читается, а одновременных записывающих пользователей нет.
PostgreSQL не даст автоматического ускорения локальной версии. Он понадобится,
если появятся несколько web-процессов/серверов, много одновременных
пользователей и записей, удалённый общий доступ, репликация или требования HA.

## Приоритетный roadmap

Порядок обязателен: сначала измерить, затем менять горячий путь. Переносить всё
в другую БД без профиля нагрузки не нужно.

### Этап 1 — воспроизводимый baseline и профилирование

- добавить `scripts/benchmark_local.py` без внешних API;
- подготовить обезличенные наборы на 3–5, 25 и 100 тысяч строк;
- измерять время загрузки, открытие результата, p50/p95 таблицы и поиска,
  полный зелёный подбор, подтверждение ID и экспорт XLSX;
- фиксировать CPU, пиковую память, число SQL-запросов и объём чтения/записи;
- добавить performance smoke в CI без жёсткой зависимости от мощности машины;
- отдельно проверить `EXPLAIN QUERY PLAN`, `ANALYZE`/`PRAGMA optimize` и
  реальные индексы на самых частых запросах.

Критерий завершения: baseline сохраняется в машиночитаемый JSON, повторный
прогон сравнивает результат с базой и показывает регрессию более 20%.

### Этап 2 — быстрые изменения с низким риском

- [x] кэшировать метаданные таблицы, нормализованные строки и ключи сортировки
  по версии сессии, а не пересчитывать их при каждом листании;
- не строить одновременно одинаковые payload для `/api/stats` и таблицы;
- [x] оставить `no-store` для пользовательских API/HTML и разрешить короткий
  безопасный кэш для CSS/JS; immutable versioned-cache остаётся следующим
  необязательным шагом;
- настроить `busy_timeout`, проверить размер WAL и выполнять обслуживание БД
  по событию/расписанию, а не в горячем запросе;
- убрать лишние DataFrame `.copy()` и полные записи XLSX из операций, которым
  достаточно изменить одну строку состояния;
- замерить 1/4/8/12 workers зелёного подбора и выбрать значение по факту, а не
  увеличивать параллелизм вслепую.

Критерий завершения: на наборе 25 тысяч строк p95 листания/поиска не хуже
300 мс на текущем компьютере, повторные действия не создают лишний XLSX, а
полный regression/E2E остаётся зелёным.

### Этап 3 — SQL-хранилище рабочего прайса

- [x] сделать таблицу `session_products` индексированным каноническим read-model;
- [x] хранить `session_id`, индекс строки, Onliner ID, название, поставщика, цены,
  гарантию, доставку, категорию и revision;
- [x] добавить индексы под фильтры: с/без ID, поставщик, категория, дубликаты и
  сортировка; для поиска по названию использовать FTS5;
- [x] выполнять фильтрацию, сортировку, счётчики и пагинацию SQL-запросами;
- [x] обновлять ID/категорию точечно в транзакции;
- [x] JSON оставить временным совместимым snapshot, а XLSX формировать только при
  скачивании/явном checkpoint;
- [x] миграцию провести с построчной сверкой и
  возможностью отката, после приёмки убрать старый внутренний путь.

Критерий завершения: результат экспорта и счётчики совпадают со старым
движком на тестовых и реальных прайсах, а горячие операции не читают и не
перезаписывают весь XLSX.

### Этап 4 — ускорение и качество зелёного подбора

- [x] кэшировать кандидатов по `catalog_revision + normalized_name + category`;
- [x] отделить извлечение кандидатов из SQLite от category-specific scoring;
- [x] исключить повторные запросы для одинаковых
  моделей и заранее вычислять часто используемые нормализованные признаки;
- [x] сохранять подтверждённые/отклонённые соответствия и считать
  precision, auto-confirm rate и false-positive rate по категориям;
- [x] использовать историю ручных решений как проверяемые правила, а не как
  безусловный глобальный ID;
- [x] добавить возобновление прерванного задания и безопасную отмену.

Критерий завершения: ускорение полного подбора минимум на 30% относительно
baseline без ухудшения precision и без роста ложных автоподтверждений.

### Этап 5 — чистая архитектура

- оставить в `app.py` создание приложения, зависимости и регистрацию
  blueprint; маршруты переносить по одному вместе с тестами;
- [x] разделить `review_candidates.py` на движок, общие признаки и плагины
  категорий;
- постепенно ликвидировать `_legacy.py`, сохраняя только подтверждённо
  используемые функции;
- ввести единые модели/константы полей товара вместо строковых названий колонок
  по всему коду;
- [x] включить обязательные Ruff, JavaScript syntax check, unit, E2E и smoke в
  один pre-push/CI-контур;
- [x] добавить type-check для новых сервисов и запрет циклических зависимостей.

Критерий завершения: новые маршруты не добавляются в `app.py`, публичные
сервисы имеют контрактные тесты, а удаление legacy не меняет пользовательские
сценарии.

### Этап 6 — новая функциональность

После этапов 1–3, чтобы функции не закрепляли старый медленный data path:

- история запусков зелёного подбора с повторным открытием отчёта;
- bulk approve/reject с preview, undo и журналом автора/времени;
- сохранённые профили поставщиков: колонки, валюта, гарантия, доставка,
  категории и наценки;
- dry-run импорта с отчётом ошибок до изменения рабочей сессии;
- шаблоны экспорта: XLSX/Google Sheets, состав колонок и правила округления;
- dashboard качества: без ID, спорные ID, дубли, точность и скорость подбора;
- сравнение двух загрузок и понятный changelog по товарам/ценам/ID;
- архив сессий с поиском и безопасным восстановлением.
